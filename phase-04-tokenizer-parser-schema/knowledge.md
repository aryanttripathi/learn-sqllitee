# Phase 4 — Front End: Tokenizer, Lemon Parser, Parse Tree, Schema

From `"SELECT name FROM users WHERE age>40"` to a tree of C structs. This phase is where
SQL stops being text.

```
  SQL text
     │  tokenize.c: sqlite3GetToken()           ── characters → tokens
     ▼
  tokens (TK_SELECT, TK_ID, TK_FROM, ...)
     │  parse.c (generated by lemon from parse.y) ── tokens → tree
     ▼
  Parse tree: Select / Expr / SrcList / ExprList
     │  resolve.c                                ── names → table/column indices
     ▼
  annotated tree (Expr.iTable, Expr.iColumn, affinity, collation)
     │  select.c / insert.c / ... + where.c
     ▼
  VDBE bytecode                                  (Phase 5)
```

## 4.1 The tokenizer

`sqlite3GetToken(const unsigned char *z, int *tokenType)` returns the length of the token
starting at `z` and sets its type. It is a hand-written switch on the first character,
driven by a 256-entry character class table:

```c
/* tokenize.c */
static const unsigned char aiClass[] = {
  /* ... maps each byte to CC_SPACE, CC_ID, CC_DIGIT, CC_QUOTE, CC_PLUS, ... */
};

int sqlite3GetToken(const unsigned char *z, int *tokenType){
  int i, c;
  switch( aiClass[*z] ){
    case CC_SPACE: { for(i=1; sqlite3Isspace(z[i]); i++){} *tokenType=TK_SPACE; return i; }
    case CC_MINUS: {
      if( z[1]=='-' ){ for(i=2; (c=z[i])!=0 && c!='\n'; i++){}
                       *tokenType = TK_SPACE; return i; }         /* -- comment */
      *tokenType = TK_MINUS; return 1;
    }
    case CC_QUOTE: { /* '...' ".." [..] `..`  with doubled-quote escapes */ }
    case CC_DIGIT: { /* integer, real, hex literal 0x... */ }
    case CC_ID:    { for(i=1; sqlite3IsIdChar(z[i]); i++){}
                     *tokenType = keywordCode((char*)z, i, tokenType); return i; }
    ...
  }
}
```

### Keyword recognition is a *generated perfect hash*

`tool/mkkeywordhash.c` emits `keywordhash.h` at build time: a table of all ~150 SQL
keywords plus a hash function chosen so that no two keywords collide. `keywordCode()` is
then an O(1) lookup with one `memcmp`. Look at the generated file — it is a beautiful,
tiny piece of engineering.

### Quoting rules (a frequent source of bugs)

| Syntax | Meaning |
|---|---|
| `'abc'` | string literal (doubled `''` escapes a quote) |
| `"abc"` | **identifier** — but if it doesn't resolve as one, SQLite falls back to treating it as a string literal (the "double-quoted string misfeature", DQS) |
| `[abc]` | identifier (MS Access/SQL Server compatibility) |
| `` `abc` `` | identifier (MySQL compatibility) |
| `X'53514C'` | blob literal |
| `?`, `?NNN`, `:name`, `@name`, `$name` | bound parameters |

DQS can be disabled at compile time (`SQLITE_DQS=0`) or per-connection
(`SQLITE_DBCONFIG_DQS_DDL`, `..._DQS_DML`). Modern advice: turn it off; it hides typos like
`WHERE name = "nmae"` which silently become string comparisons.

### The parse driver

```c
int sqlite3RunParser(Parse *pParse, const char *zSql){
  ...
  while( zSql[i]!=0 ){
    pParse->sLastToken.z = &zSql[i];
    pParse->sLastToken.n = sqlite3GetToken((u8*)&zSql[i], &tokenType);
    i += pParse->sLastToken.n;
    if( tokenType>=TK_SPACE ){          /* TK_SPACE, TK_ILLEGAL are >= TK_SPACE */
      if( tokenType==TK_ILLEGAL ){ ... error ... }
      continue;                          /* whitespace/comments never reach the parser */
    }
    sqlite3Parser(pEngine, tokenType, pParse->sLastToken);   /* ← the LALR machine */
    if( pParse->rc!=SQLITE_OK || db->mallocFailed ) break;
  }
  sqlite3Parser(pEngine, 0, pParse->sLastToken);             /* end of input */
}
```

One token at a time, pushed into the parser. There is no separate token array — SQLite
streams.

## 4.2 Lemon and `parse.y`

Lemon (`tool/lemon.c`, ~5000 lines) is SQLite's own LALR(1) parser generator. It differs
from yacc/bison in ways that matter:

- **Non-terminal destructors** (`%destructor`) — every partially built tree node is freed
  automatically on a syntax error. No leaks even in the middle of a malformed statement.
- **No global variables** — the parser is reentrant, state lives in `yyParser`.
- **Token values are non-terminal-typed** via `%type`, so the grammar is type-checked C.
- **`%fallback`** — lets keywords be used as identifiers when unambiguous. This is why
  `CREATE TABLE t(key, value)` works even though `KEY` is a keyword:
  ```
  %fallback ID  ABORT ACTION AFTER ANALYZE ASC ATTACH BEFORE BEGIN BY CASCADE CAST
                COLUMNKW CONFLICT DATABASE DEFERRED DESC DETACH DO EACH END ...
  ```
- **`%wildcard ANY.`**, **`%syntax_error`**, **`%stack_overflow`** blocks.

Grammar excerpt (real, slightly trimmed):

```
%left OR.
%left AND.
%right NOT.
%left IS MATCH LIKE_KW BETWEEN IN ISNULL NOTNULL NE EQ.
%left GT LE LT GE.
%right ESCAPE.
%left BITAND BITOR LSHIFT RSHIFT.
%left PLUS MINUS.
%left STAR SLASH REM.
%left CONCAT.
%left COLLATE.
%right BITNOT.

cmd ::= select(X).  { sqlite3Select(pParse, X, &dest); sqlite3SelectDelete(db, X); }

select(A) ::= WITH wqlist(W) selectnowith(X). { A = attachWithToSelect(pParse,X,W); }

oneselect(A) ::= SELECT distinct(D) selcollist(W) from(X) where_opt(Y)
                 groupby_opt(P) having_opt(Q) orderby_opt(Z) limit_opt(L). {
  A = sqlite3SelectNew(pParse,W,X,Y,P,Q,Z,D,L);
}

expr(A) ::= expr(X) PLUS expr(Y).   { A = sqlite3PExpr(pParse, TK_PLUS, X, Y); }
expr(A) ::= expr(X) EQ   expr(Y).   { A = sqlite3PExpr(pParse, TK_EQ,   X, Y); }
```

The action blocks in `{...}` are plain C that builds the tree. **`parse.y` is therefore
both the grammar and half the front end.**

Practical notes:
- Lemon reports conflicts at build time; the SQLite grammar is kept **conflict-free**.
- The parser stack has a fixed max depth (`YYSTACKDEPTH`, dynamically grown by default);
  `SQLITE_LIMIT_SQL_LENGTH` and `SQLITE_MAX_EXPR_DEPTH` protect against hostile input like
  `((((((...))))))` a million deep.

## 4.3 The parse tree structures

### `Expr` — the workhorse

```c
struct Expr {
  u8 op;                 /* TK_PLUS, TK_COLUMN, TK_INTEGER, TK_FUNCTION, TK_AGG_COLUMN... */
  char affExpr;          /* affinity of this expression */
  u8 op2;                /* TK_COLUMN: original op; TK_AGG_FUNCTION: parent op */
  u32 flags;             /* EP_xxx */
  union {
    char *zToken;        /* literal text, column/function name */
    int iValue;          /* integer value if EP_IntValue */
  } u;
  Expr *pLeft, *pRight;  /* operands */
  union {
    ExprList *pList;     /* function args / IN(list) */
    Select *pSelect;     /* subquery: IN(SELECT...), (SELECT...) */
  } x;
  int iTable;            /* cursor number (after name resolution) */
  ynVar iColumn;         /* column index in the table, or -1 for rowid */
  i16 iAgg;              /* index into AggInfo */
  AggInfo *pAggInfo;
  union { Table *pTab; Window *pWin; int iValue; } y;
};
```

Important `EP_*` flags: `EP_FromJoin`/`EP_OuterON` (term came from a join's ON clause —
critical for outer-join correctness), `EP_Agg` (contains an aggregate), `EP_Collate`,
`EP_IntValue`, `EP_Subquery`, `EP_Constant`, `EP_Win`, `EP_Skip`, `EP_TokenOnly`/
`EP_Reduced` (memory-compressed forms used when storing an `Expr` in a schema object).

```
   WHERE age > 40 AND name LIKE 'a%'

                   TK_AND
                  /      \
             TK_GT        TK_LIKE (TK_FUNCTION 'like')
            /     \            \
     TK_COLUMN  TK_INTEGER   ExprList[ TK_COLUMN name, TK_STRING 'a%' ]
     iTable=0   u.iValue=40
     iColumn=2
```

### `ExprList`, `SrcList`, `Select`

```c
struct ExprList {
  int nExpr;
  struct ExprList_item {
    Expr *pExpr;
    char *zEName;        /* name/alias */
    struct { unsigned done:1, reusable:1, bSorterRef:1, bNulls:1, ... } fg;
    union { struct { u16 iOrderByCol; u16 iAlias; } x; int iConstExprReg; } u;
    u8 sortFlags;        /* KEYINFO_ORDER_DESC / _BIGNULL */
  } a[1];                /* grown by realloc — classic C flexible array */
};

struct SrcList {         /* the FROM clause */
  int nSrc;
  SrcItem a[1];
};
struct SrcItem {
  Schema *pSchema; char *zDatabase, *zName, *zAlias;
  Table *pTab;           /* filled in by name resolution */
  Select *pSelect;       /* if it is a subquery */
  int addrFillSub, regReturn, regResult;
  u8 fg.jointype;        /* JT_INNER, JT_LEFT, JT_CROSS, JT_RIGHT, ... */
  int iCursor;           /* THE CURSOR NUMBER assigned to this table */
  Expr *pOn; IdList *pUsing;
  Bitmask colUsed;       /* which columns are referenced — drives covering-index choice */
  Index *pIBIndex;       /* INDEXED BY */
};

struct Select {
  ExprList *pEList;      /* result set */
  u8 op;                 /* TK_SELECT, TK_UNION, TK_ALL, TK_INTERSECT, TK_EXCEPT */
  LogEst nSelectRow;     /* estimated result rows */
  u32 selFlags;          /* SF_Distinct, SF_Aggregate, SF_All, SF_Resolved, SF_Compound... */
  SrcList *pSrc; Expr *pWhere; ExprList *pGroupBy; Expr *pHaving;
  ExprList *pOrderBy; Select *pPrior, *pNext; Expr *pLimit;
  With *pWith; Window *pWin; ...
};
```

**`iCursor` is the bridge to Phase 5**: each table reference in the FROM clause gets a
cursor number, and the generated bytecode's `OP_OpenRead P1` is exactly that number.

## 4.4 Name resolution (`resolve.c`)

The parser does not know that `name` is column 1 of `users`. Resolution does, using a
`NameContext` chain:

```c
struct NameContext {
  Parse *pParse;
  SrcList *pSrcList;      /* tables in scope */
  union { ExprList *pEList; AggInfo *pAggInfo; Upsert *pUpsert; } uNC;
  NameContext *pNext;     /* ← outer query, for correlated subqueries */
  int nRef;               /* how many names resolved to this context */
  int nNcErr;
  int ncFlags;            /* NC_AllowAgg, NC_HasAgg, NC_IsCheck, NC_PartIdx, NC_IdxExpr ... */
};
```

`lookupName()` resolution order for `a.b.c`:
```
 1. treat as database.table.column
 2. else table.column (or alias.column)
 3. else column in any table of pSrcList (ambiguity ⇒ error)
 4. else a result-set alias of the current SELECT (only in ORDER BY/GROUP BY/HAVING)
 5. else a name in an outer NameContext  ⇒ mark the subquery CORRELATED
 6. else error: "no such column"
```

On success it sets `pExpr->op = TK_COLUMN`, `pExpr->iTable = <cursor>`,
`pExpr->iColumn = <column index>`, and the expression's affinity/collation.

The traversal uses the generic `Walker` from `walker.c`:
```c
struct Walker {
  Parse *pParse;
  int (*xExprCallback)(Walker*, Expr*);     /* WRC_Continue / WRC_Prune / WRC_Abort */
  int (*xSelectCallback)(Walker*, Select*);
  void (*xSelectCallback2)(Walker*, Select*);
  union { NameContext *pNC; int n; SrcList *pSrcList; ... } u;
};
```
You will meet `Walker` again in the optimizer (constant propagation, subquery flattening,
`WHERE`-clause pushdown). Learning it once pays off three times.

## 4.5 The schema in memory

```c
struct Schema {
  int schema_cookie;      /* must match the value in the db header */
  int iGeneration;        /* bumped on every schema change */
  Hash tblHash, idxHash, trigHash, fkeyHash;   /* name → Table*/Index*/Trigger*/FKey* */
  Table *pSeqTab;         /* sqlite_sequence, for AUTOINCREMENT */
  u8 file_format, enc;
  u16 schemaFlags;        /* DB_SchemaLoaded, DB_UnresetViews, DB_Empty */
};

struct Table {
  char *zName;
  Column *aCol; i16 nCol;
  Index *pIndex;          /* linked list of indexes on this table */
  Pgno tnum;              /* ROOT PAGE of the table b-tree */
  LogEst nRowLogEst;      /* estimated row count (from sqlite_stat1) */
  LogEst szTabRow;        /* estimated average row size */
  u32 tabFlags;           /* TF_WithoutRowid, TF_HasPrimaryKey, TF_Autoincrement, ... */
  i16 iPKey;              /* column that is the INTEGER PRIMARY KEY (rowid alias), or -1 */
  union { struct {...} tab; struct { Select *pSelect; } view; } u;
  Trigger *pTrigger; FKey *pFKey; ...
};

struct Index {
  char *zName;
  i16 *aiColumn;          /* which table columns; -1 = rowid, -2 = expression */
  LogEst *aiRowLogEst;    /* aiRowLogEst[0]=rows, [i]=avg rows per distinct prefix of i cols */
  Table *pTable; Index *pNext;
  Pgno tnum;              /* root page */
  const char **azColl;    /* collation per column */
  Expr *pPartIdxWhere;    /* partial index WHERE clause */
  ExprList *aColExpr;     /* expressions, for expression indexes */
  u8 onError;             /* OE_None/Abort/Replace/... for UNIQUE */
  unsigned idxType:2;     /* 0=CREATE INDEX, 1=UNIQUE constraint, 2=PRIMARY KEY */
  unsigned uniqNotNull:1, isCovering:1, hasStat1:1, bNoQuery:1, ...;
};
```

### Bootstrapping (`prepare.c`)

```
sqlite3ReadSchema()
  └─ sqlite3InitOne(db, iDb, ...)
       1. hard-code the definition of sqlite_schema (root page 1)
       2. read the header: page size, text encoding, schema cookie, file format
       3. run:  SELECT name, rootpage, sql FROM "main".sqlite_schema ORDER BY rowid
       4. for EACH row, call sqlite3InitCallback():
            - RE-PARSE the stored CREATE statement with a special flag
              (db->init.busy = 1, db->init.newTnum = rootpage)
            - the parser builds the Table/Index object and installs it in the hash,
              using the stored root page instead of allocating one
       5. mark DB_SchemaLoaded
```

**SQLite's schema is stored as SQL text and re-parsed on every connection.** That is why:
- `ALTER TABLE RENAME` must rewrite the text of dependent objects,
- a corrupt `sql` column makes the database unopenable (`PRAGMA writable_schema` exists to
  repair exactly that),
- `sqlite3_prepare` may return `SQLITE_SCHEMA`: if another connection changed the schema,
  the cached schema is stale. `prepare_v2` retries automatically.

`PRAGMA schema_version` is that cookie; every DDL bumps it, invalidating everyone's
prepared statements.

## 4.6 Type affinity and collation — decided here, applied everywhere

### Affinity determination (from the declared type text)

```
1. contains "INT"                          → INTEGER
2. contains "CHAR", "CLOB", or "TEXT"      → TEXT
3. contains "BLOB", or type is empty       → BLOB  (a.k.a. "none")
4. contains "REAL", "FLOA", or "DOUB"      → REAL
5. otherwise                               → NUMERIC
```

That is `sqlite3AffinityType()` in `build.c`, and it explains delightful facts such as
`VARCHAR(10)` → TEXT, `FLOATING POINT` → INTEGER (it contains "INT"!), and
`STRING` → NUMERIC.

Affinity is applied:
- on **storage**: `OP_MakeRecord`'s P4 affinity string converts values before the record
  is built,
- on **comparison**: `OP_Eq` & friends apply the comparison affinity rules
  (`sqlite3CompareAffinity`), which is why `'1' = 1` is true for an INTEGER column but
  false for two literals.

### Collating sequences
Built-in: `BINARY` (memcmp), `NOCASE` (ASCII-only case folding), `RTRIM`.
Precedence when comparing: an explicit `COLLATE` on either operand wins; otherwise the
left operand's column collation; otherwise the right's; otherwise BINARY.
`sqlite3ExprCollSeq()` implements the walk. Index usability depends on it: an index on
`name` (BINARY) cannot serve `WHERE name = ? COLLATE NOCASE`.

## 4.7 `sqlite3NestedParse()` — SQLite writing SQL to itself

DDL is implemented by generating SQL:

```c
sqlite3NestedParse(pParse,
   "UPDATE %Q." LEGACY_SCHEMA_TABLE " SET rootpage=%d WHERE #%d AND rootpage=#%d",
   db->aDb[iDb].zDbSName, iTo, iReg, iFrom);
```

`%Q` quotes an identifier, and `#N` means "the value currently in VDBE register N" — a tiny
extension to the SQL syntax available only to nested parses. `CREATE TABLE`, `ALTER TABLE`,
`DROP`, and auto-vacuum root-page fixups all use it. It keeps the schema-modification code
short at the price of some runtime parsing.

## 4.8 Triggers and views (front-end view)

- **Views** are stored as their `SELECT` text; at use time `sqlite3ViewGetColumnNames()`
  parses it and the view is either flattened into the outer query or materialized as a
  co-routine/ephemeral table.
- **Triggers** are parsed into a `Trigger` + chain of `TriggerStep` (each holding the
  statement's own parse tree). At code-generation time the trigger program is compiled as a
  **sub-program** (`OP_Program`), with `OLD.`/`NEW.` rows living in a `VdbeFrame`'s
  registers.

```c
struct TriggerStep {
  u8 op;                 /* TK_UPDATE, TK_INSERT, TK_DELETE, TK_SELECT */
  Select *pSelect; SrcList *pFrom; Expr *pWhere;
  ExprList *pExprList; IdList *pIdList; Upsert *pUpsert;
  char *zTarget; TriggerStep *pNext, *pLast;
};
```

## 4.9 Debugging the front end

Debug builds give you tree printers:

```
sqlite> .treetrace 0xffff        -- (older name: .selecttrace) dump Select transformations
sqlite> .wheretrace 0xfff
sqlite> PRAGMA parser_trace=ON;  -- if compiled with SQLITE_DEBUG: Lemon shift/reduce trace
```

In C / the debugger:
```c
sqlite3TreeViewExpr(0, pExpr, 0);
sqlite3TreeViewExprList(0, pList, 0, "eList");
sqlite3TreeViewSelect(0, pSelect, 0);
sqlite3TreeViewSrcList(0, pSrc);
```
`treeview.c` output looks like:
```
SELECT
├── result-set
│   └── COLUMN users.name
├── FROM
│   └── {0:0} users
└── WHERE
    └── GT
        ├── COLUMN users.age
        └── INTEGER 40
```

Learning to read that output is the fastest way into `select.c` (Phase 5–6).
